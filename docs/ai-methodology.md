# AI methodology — how this application was built, and how it uses LLMs

The assignment asks for the application to be generated with AI tools/agents, and for a
summary of the LLMs chosen and the agent instructions given. This document covers both:
first the LLM usage **inside** the product, then the AI-assisted process that **built** it.

## 1. LLMs inside the product

| Concern | Choice | Why |
|---|---|---|
| Analysis model (default) | `stub-analyst-v1` — deterministic in-process stub | The assignment allows stubs. The stub derives risk level, findings and recommendations from the risk-rule signals and emits **exactly the JSON contract a real model is prompted for**, so the entire pipeline (RAG retrieval, prompt audit, parsing, validation, persistence, UI) is production-shaped and the demo runs offline with zero keys. |
| Analysis model (real) | Anthropic Claude (`claude-sonnet-5` by default, configurable) via the Messages API | Strong structured-output reliability and long-context reasoning over the activity digest + policy excerpts. Selected automatically when `ANTHROPIC_API_KEY` is set (`caa.llm.provider=auto`), switchable per environment. |
| Embeddings | Deterministic feature-hashing model (in-process, 384-dim) behind an `EmbeddingModel` port | Anthropic offers no embeddings API; rather than hard-wiring a second vendor, retrieval runs on a dependency-free hashed bag-of-words model that is honest about being lexical. The port + pgvector store are exactly what a hosted embedding model (e.g. Voyage) would plug into. |

Guardrails applied to model output: strict JSON schema in the system prompt; risk level
validated against the enum; cited policy chunk ids accepted **only** if they were actually
retrieved (hallucinated citations dropped); non-UUID transaction references dropped;
malformed responses persist as `FAILED` runs instead of vanishing. Prompts are
pseudonymised (customer number, never name/email/DOB) and stored with the raw response for
audit.

## 2. How the application was generated

Built with **Claude Code** (Anthropic's agentic CLI) running **Claude Fable 5**, in a
single supervised session, with one subagent used for parallelism.

### Method

1. **Spec first.** The assignment PDF was decomposed into the five spec points; schema and
   API were designed before any code: `docs/api-contract.md` was written and committed
   first and declared binding for both sides.
2. **Standing agent instructions.** `CLAUDE.md` at the repo root carries the rules the
   agent must follow across the whole session (see summary below). This file is the
   "agent instructions" artefact and stays in the repo.
3. **Deterministic data before features.** The demo dataset is generated by
   `scripts/generate_seed_data.py` (committed, seeded RNG): 8 behaviour archetypes and a
   re-implementation of the 10-rule risk catalogue over the generated timeline, so seeded
   `risk_assessments` are consistent with the rules they reference — the AI analysis then
   has something real to reason about.
4. **Backend built by the main agent; frontend delegated to a subagent** working only in
   `frontend/` against the frozen API contract — the contract-as-interface is what made
   parallel agent work safe.
5. **Tests as the feedback loop.** 21 unit tests (stub analyst bands, embedding
   determinism, prompt pseudonymisation, failure paths, citation validation, auth) plus a
   Testcontainers integration test walking the full operator journey.
6. **Adversarial review pass.** After the app worked end-to-end, a multi-agent review
   (separate reviewer agents for spec compliance, security, correctness and docs accuracy,
   with findings adversarially verified before being acted on) ran over the final diff,
   and confirmed findings were fixed before delivery.

### Summary of agent instructions given

- **Repo-wide (`CLAUDE.md`)**: API contract is the source of truth and changes contract-first;
  Flyway migrations are append-only; no real PII anywhere and seed data must be
  deterministic; the app must run fully offline (stub LLM default, real adapters
  config-only); secrets only via environment; Java conventions (constructor injection,
  records for DTOs, no Lombok, RFC 7807 errors); frontend conventions (TS strict, API
  types mirroring the contract, no extra UI libraries); testing expectations.
- **Frontend subagent brief**: build the operator dashboard against `docs/api-contract.md`
  exactly; allowed deps react/react-dom/react-router-dom only; hand-rolled SVG chart;
  JWT session handling with 401 redirect; defined pages (login, search, customer
  dashboard with overview cards, monthly chart, triggered-rules panel, filtered
  transactions with expandable type-specific details, AI analysis panel with history);
  a shared risk-color convention; must pass `npm run build` (tsc) before finishing.
- **Reviewer agents' brief**: find deviations from the assignment spec and the API
  contract, security issues, and correctness bugs in the final tree; every finding
  verified against the actual code before being reported.
